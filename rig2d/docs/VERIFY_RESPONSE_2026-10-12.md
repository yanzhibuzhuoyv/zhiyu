### 1.2 T1e —— 「紧凑 vs 退化」判据（两次失败后定型）

核实报告列了 4 个候选信号。我实做了两个，都失败，如实记录：

| 尝试 | 信号 | 结果 |
| --- | --- | --- |
| 一 | 行内笔画**计数**的底部/顶部比 | **两案例全判反**。计数反映纹理密度而非轮廓：头在下巴处轮廓收窄，但眼睛与嘴集中中下部 → 计数反而变大；「头+躯干」框下半部笔画稀疏（衣服线淡）→ 计数变小 |
| 二 | 行内笔画**轮廓宽度**的底部/顶部比 | 合成彩图可用（头 1.06 vs 躯干 1.46），**真实线稿失效**：人物的手抬在下巴前，正在框的下部，把轮廓撑宽（实测 `w50=0.94, w90=0.925, bottom_growth=2.07`），紧凑头被判成躯干。**那是真实内容，不是缺陷** |
| **定型** | **贴边**为主 + 「下部变宽 **且** 框高占画面 >75%」为辅 | 5/5 案例正确 |

定型判据（`head_vs_body_shape`）：

```
拒绝，若满足任一：
  · 框同时贴住画面右侧与底部          ← 自动定位一路扩到边缘的典型症状
  · 贴住 ≥2 条画面边缘
  · 框宽 ≥92% 且框高 ≥92% 画面        ← 退化成了整幅图
  · bottom_growth > 1.40 且 框高占画面 > 0.75
```

最后一条的两个条件**必须同时成立**：单用 `bottom_growth` 会被「头+手」的真实构图误伤。

## 4. T1f：合成 front 0.0769 的成因（已量化）

核实报告的质疑是对的：**合成夹具的几何是参数化生成的，说「几何拟合差异」需要一个解释**。
我写了专门的诊断脚本 [diagnose_front_holes.py](../probe/diagnose_front_holes.py)，
对每个 front 空洞像素反解它在源图上的对应像素，看该源像素属于角色还是背景。

### 4.1 结果

```
front_hole_ratio           = 0.07695
holes_on_background_source = 5793     (99.84%)
holes_on_character_source  =    9     ( 0.16%)
holes_off_image            =    0
verdict = GEOMETRIC_FIT
```

### 4.2 机制（直接量，非推断）

```
代理足迹在源图坐标下: 列 207..562, 行 137..624     ← 恰好等于 head_box
代理足迹内像素: 160317
  属角色(alpha=True) : 145387 (90.7%)
  属背景(alpha=False):  14930 ( 9.3%)   ← front 空洞的来源
```

**代理的正面足迹是圆角矩形（超椭球 p=4），它 90.7% 落在角色 alpha 内、9.3% 落在 alpha 外。**
那 9.3% 的几何在正面可见、但源图在那里没有角色像素，于是被记为空洞。
渲染时还叠加上采样与膨胀的边界效应，最终比值落在 7.7%（baseline）。

### 4.3 结论

- **不是新引入的误差**：它由头框尺寸与超椭球填充系数的关系决定（p=4 的圆角矩形装不满矩形框）。
- **也不是「投影丢了纹理」**：只有 9/5802 个空洞对应角色像素，属噪声量级。
- **可验证的预测**：若把代理换成更贴合头部轮廓的形状（或缩小覆盖到内容形状内），
  这个比值应显著下降。这正是 FRAMING_DEFECT §7 方案丙要做的。

### 4.4 第一次诊断得到的是**相反**的结论（记录在案）

第一版诊断脚本 `holes` 的源像素反解用了 `pixel_scale` 硬推、并把符号算错，
得出「72.9% 空洞对应角色像素 → `TEXTURE_DEFECT`」的**假结论**。
幸好我对该结论做了自洽性检查（用 `render_view` 的取景公式重算了一遍命中掩码），
发现不一致才定位到反解公式。

**教训**：反解必须复用产生该渲染的**同一个取景公式**（取景是自适应的），
不能用 `pixel_scale` 另行推算。脚本里已写明这条。

## 7. T4：新增合成线稿夹具（`NEXT_DUAL_INPUT` §4.2）

`NEXT_DUAL_INPUT` 指出：**线稿路径没有可信对照物**——现有合成夹具是彩图，
用它量出来的数对线稿无意义（身份载体不同）。本轮补上。

### 7.1 夹具设计（[synthetic_line_art.py](../probe/synthetic_line_art.py)）

| 属性 | 做法 | 为什么 |
| --- | --- | --- |
| 载体 | 白底 + 深色笔画（灰度 0.18），**脸内部是纸色** | 这正是彩图定位法在线稿上必失效的原因；不还原这一点就测不出真实工况 |
| 几何真值 | 脸/头发是解析椭圆，笔画只画在区域**边界**上 | 「头在哪、笔画该出现在哪」都可计算，能核对探针的定位与空洞面积 |
| alpha 语义 | **头部闭合区域并集**，不是暗像素 | 线稿按暗像素取 alpha 会把脸内部当背景；真实线稿资产同样需要「角色区域」这一层 |
| 非对称 | 左侧碎发更厚更长、右眼略小 | 与彩图夹具同一考虑：不让 A 级收益被「本来就是镜像」夸大 |
| 确定性 | 无随机数 | 可复跑 |

参数：`--fixture line_art`（同时保留 `--fixture color` 为默认）。

### 7.2 首次跑通的结果

| 项 | 值 |
| --- | --- |
| profile / 判定角 | `line_art` / ±45°，`worst_90 = not_applicable` |
| **头框来源** | **`auto`**（自动定位）——这是**第一次**在单色输入上自动成功 |
| 自动头框 | `[189, 116, 579, 690]` |
| **几何真值头框** | `[189, 123, 579, 593]` |
| 列方向误差 | **0 像素**（189/579 完全一致） |
| 行方向误差 | 上 +7px、下 +97px（下沿多含了脖子底座，属合理宽松） |
| 笔画像素占比 | 1.78%（线稿真实工况：稀疏） |
| 纹理有效格占比 | 0.157 |
| front baseline → B | 0.2125 → 0.0670 |
| ±45° baseline → B | 0.4318 → 0.2702 / 0.2713 |

产物：`artifacts/rig-probe-synth-lineart-2026-10-12/`。

**门禁结论：`GATE_FAIL_STOP_AND_RENEGOTIATE`**（±45° 残留 27.1% > 25%）。
这是一条**真实且方向合理**的对照结果，不应被淡化：

| 输入 | profile | 判定角 | ±45° B | gate |
| --- | --- | --- | --- | --- |
| 合成彩图 | `color` | ±90° | 0.2103 | `NEEDS_C` |
| **合成线稿（新）** | `line_art` | ±45° | **0.2713** | **`FAIL_STOP_AND_RENEGOTIATE`** |
| 真实线稿 | `line_art` | ±45° | 0.1580 | `NEEDS_C` |

原因：夹具的笔画是**均匀细轮廓线**（仅 1.78% 像素），有效纹理极稀疏，
A/B 可搬运的像素本来就少。而那张真实铅笔稿的头发与眼睛区域笔画密集得多
（`alpha` 由背景泛洪给出，包含大量笔画附近像素），因此残留明显更低。

**这说明线稿路径的 `hole_ratio` 强烈依赖笔画的疏密分布**，
不能把「残留低」直接读成「补全能力强」——它可能只是「笔画密、可搬运的像素多」。
这正是 `NEXT_DUAL_INPUT` §4.2 要求线稿另设判据（笔画连续性/断头率）的量化依据。

### 7.3 该夹具暴露的一个真问题：线稿的 gate 判据没有闭环

合成线稿跑出 `FAIL_STOP_AND_RENEGOTIATE`（27.1% > 25%），而真实线稿是 `NEEDS_C`（15.8%）。
两者都是线稿、都是 ±45°、都走同一套判据，却分处不同档位。

**说明线稿路径当前只有一档面积阈值，不足以支撑判定**——差异来源是笔画密度，
而笔画密度不是补全质量的度量。**因此在线稿的笔画拓扑判据做出来之前，
线稿的 gate 结论都应视为不完整。**

---

线稿夹具的 ±45° 残留（B 后 **27.0%**）**高于**真实线稿（B 后 **15.8%**）。
方向合理：夹具的笔画是**均匀细线**（只有轮廓，内部无线），而真实铅笔稿的
头发与眼睛区域笔画密集得多。这说明残留率**强烈依赖笔画的疏密分布**——
因此线稿路径的判据若只看 `hole_ratio`，会把「笔画密度」误读成「补全质量」。
这正是 `NEXT_DUAL_INPUT` §4.2 要求的「线稿需另设判据（笔画连续性/断头率）」的量化依据。

**本轮未实现笔画连续性/断头率判据**（属 T4 的后半段），因此线稿路径目前仍只有面积判据。
