# VoiceMem 本地语义检索可取性：首轮 A/B

结论：本轮没有把 VoiceMem 整套引入 Android。对“派生分区路由后再语义排序”做了真实同库实验；这个简化 IVF 候选没有满足保持原召回的门槛，暂不接入生产。原 RAG 的原文、语义优先、精确补漏和三层标注均未改动。

## 原理与适配边界

已核对[论文原文](https://arxiv.org/html/2608.26005v1)与[作者代码库](https://github.com/xzf-thu/VoiceMem)。论文的可取点是上层 schema/实体路由先限制候选池，再由可替换的下层引擎排序；语音中可提前查询。134 ms 是论文实验中的检索阶段，不是我们的手机、十万原文分块或完整回答延迟。

原工程还有事实提取和更新流程，不能直接替换本项目的逐条原文存储。我们可以独立建立只含原文 ID 的派生路由索引，保留作者、时间、SHA、revision，再返回独立原话。本实验只借鉴“先限定候选池再排序”，没有重现论文的实体关系图、图扩展与演化，失败不等于否定论文整体。

语音预取值得后续独立验证，但不能只在 ASR partial 时启动一次完整的慢检索便宣称解决延迟。预取必须可取消，按聊天、查询、索引版本校验，partial 不写入对话、不调用付费回复；最终查询改变时必须丢弃旧结果。当前未接入预取，因此没有伪造它的提速数据。

## 可复现输入

- 只读来源：`artifacts/fifty-million-resume-r9c-failed.sqlite3`，851,152,896 bytes。
- 文件名是历史查询断言失败时留下的诊断快照；本次只读检查实际包含 5,000 条原文、5,000 ready jobs 和 100,000 个完整真实 BGE 向量。它不是最终 r9h 设备现场，未重跑五千万写入/索引任务。
- 仅有 owner `synthetic-fifty-million`；无用户聊天、Key、云调用。全部消息 active/mid，user 和 assistant 各 2,500 条；没有 annotation。
- 全部 100,000 条分别验证向量 blob SHA、原文 SHA/revision 的元数据对应关系、512 维和归一化。未改写或解压重存原文。
- 模型为正式手机相同的 `bge-small-zh-v1.5` INT8 ONNX，SHA `a20c8811f4c52f72f31783c615b6a6ea2eaac6b8b52eea5a107e004f4cc632f7`；本地 tokenizer 的 vocab/config/tokenizer_config SHA 与手机固定身份一致。无下载。
- 数据库开始/结束 SHA 都为 `8373be4371ae7182f35f73889ceeac4bdefe4ffded176d43ce27cac415c4c4f0`。
- 24 条预先固定的自然问题，包含旧四题、未用于分区训练的转述和无答案问题；另有 2 组多向量 max reducer 检查。每项测 3 次，共 78 次测时，不是 78 条独立问题。

## 方法

A 为全量精确语义扫描。评分采用 Float32 乘积、Float64 累加，和 Kotlin 当前 `score += Float * Float` 一致；多 query 取最大值。按不同原文 ID 归并后排序，保留 `.42` 候选阈值、原 role/seq 次序、最多 8 条。本库全为 mid 且 annotation factor=1，不代表已经验证全部分层条件。

B 为 64 质心的派生 IVF：固定 seed=20261015，在无查询参与的 20,000 条真实向量样本上拟合 MiniBatchKMeans；全部十万向量建立 ID 分区；分别查询 1/4/8/16/32/64 个最近分区，再使用 A 的同一精确评分与排序。原文不合并，不由质心替代证据。上线门槛事先固定为本组每条查询的 top-8 ID 及顺序均与 A 一致，仍需额外 Android/dirty/cold 验证才可采用。

精确语义阶段为空不代表全 RAG 失败：生产还有精确词法补漏，本轮没有测完整的原文返回/纠正链，也没有把无 gold 标签的相似度前八称为事实准确率。

构建约 956.159 ms；质心 131,072 B、分区数组 400,000 B、row→原文映射 400,000 B，NPZ 931,838 B；不包含 204,800,000 B 向量矩阵、候选临时数组、逐维乘法中间内存。没有因此宣称手机只增加不到 1 MB 内存。桌面 query 编码 p50 2.783 ms，首条最大 11.791 ms，另行测量，没有混入表中评分时间。

## 正确解读与后续

这些是 Windows/Python/NumPy CPU、已在 RAM 的向量评分结果，不是 Kotlin、AVD、红米或完整 SQLite/RAG 结果，也不能拿 83 ms 直接除以旧 20 秒称为手机加速倍数。生产还逐行读取/校验 blob、读取分层标注、原文解压校验和做必要补漏。原库由大量模板长文及随机汉字构成；不能代表十年自然聊天或全部冷库/更正场景。

本次拒绝把这个近似路由候选加到生产。后续更稳妥的最小实验是原生同一合成库先量 cursor I/O、SHA、向量乘加、annotation 和原文材料化分项，再试有界、版本化的批量精确评分或缓存：仍保持 SHA 校验、原文 ID、全部候选与同一排序；分别测冷启动、暖查询、索引变更后、active/cold/更正与取消，全部结果对齐后再采用。不能为了论文的 134 ms 口号省掉校验或偷偷改变召回。
