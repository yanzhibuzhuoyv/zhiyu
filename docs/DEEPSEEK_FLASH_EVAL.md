- 语义案例直接使用生产 `_messages` 和 `parse_response`；回复案例使用生产 `prompt`，服务器时间冻结为 `2026-10-06T04:00:00+00:00`。每个案例在不同模式下的输入相同，测试前保存输入、期望断言与源码 SHA，结束后核对源码未变。

- 回复 regex 只筛查事实与关键表述。两次重复形成 8 对 A/B 盲评，按原文依据、情绪回应与具体陪伴逐条定性复核，不拼成情感质量总分。这是单个 Codex 模型评审，未进行人类用户满意度研究。
- 延迟是非流式完整响应耗时，不是首字延迟。15 秒指标表示满足固定语义断言且在现有识别预算内完成；另外报告纯格式与完成情况。未实际用 15 秒提前取消本次请求，以便观察迟到与截断结果。
- Token 使用 API 返回 usage；未返回的细项保持未知。思考全文不落盘，只存字符数和官方返回的 reasoning token 数。费用按测试时空闲时段的缓存命中/未命中/输出单价估算，不是控制台账单。

## 具体错误与产品意义

- **愿望、偏好与作者**：开启模式两次正确识别今晚愿望（S05）以及AI自身承诺、非用户的第三人愿望（S07）；关闭模式这两题各0/2通过。开启更有利于本组复杂语义边界，但不能单凭自报 confidence 证明真实理解。
- **历法**：未明说公农历的“八月初三”，两种模式都猜农历。后端都清掉未经原话支持的历法；关闭模式还两次错误给出 `explicit_keep=true`。解析器能保护来源与部分历法规则，不能自动证明所有语义字段正确。
- **输出预算**：开启模式 S04一次、S06一次、S11两次、S12两次均以 `finish_reason=length` 结束，4096输出token全是思考，最终内容空。这六次明确计失败，没有用扩大预算重跑掩盖。
- **严格原文位置**：关闭模式S06一次给错字符位置、S10一次把JSON null写成字符串；S12两次没有为重复quote正确提供来源位置。严格校验拒绝整次识别，这会保留正常聊天原文而不落不可靠标注。
- **探索性发现，未计入固定总分**：部分关闭模式输出在没有明确保存请求时滥标 `explicit_keep=true`，包括S11愿望。这可能把普通关注错误保护为永久，影响三层与空间策略。部分题目的预注册断言没有覆盖该字段；不能把上表断言通过当全部标签可信。应针对该字段补专门回归与确认门槛。
- **聊天仍会添事实或承诺**：关闭模式R03第二次把“承诺9月25日陪整理”说成“9月25日那天答应”，混淆约定日与保存/承诺日期；R04第一次在检索未完成时断言完全没有爸爸名字记录。开启模式有“以后每年都不会弄错”的绝对承诺，以及R02第二次提议把两次愿望记成喜欢海边。regex都无法可靠捕捉这些上下文问题，需逐条复核。

用户提出日常分享也每轮检索会拖慢、不自然。代码核对：目前`chat_routes.send`依次旧记忆/知识库检索→聊天生成→额外语义标注→保存→返回；用户看到回答前仍会等标注。等待路径测试没有运行实际BM25/冷召回，因此23–28秒的后置思考识别不能归因给RAG查询。当前生产识别仍受15秒截止，与本轮放开等待的测试不同。

建议区分三个问题：“当下怎么回应”“是否需要旧记忆”“新原话是否需要标签”，同一句可同时是分享和记忆来源。分享/情绪优先回应当下；指代、约定、更正、明确回忆等提升召回需要。先复用近期原文上下文，再做有界本地候选查询；只有对当前回应有帮助的旧原文才注入，不因存在命中就复述往事或劝阻用户。相关性、来源可信度、情绪适配和刚提过的内容均须独立评估；拟人性不能通过随机遗漏生日、约定或更正来模拟。

不宜增加每轮等待的云端“是否检索”思考调用。可评估轻量多标签路由，低置信度保留有界本地检索兜底；不能只凭几个关键词判“闲聊”就关闭记忆。流式聊天、完整原文落库与持久任务记录应先完成，层级识别在后台按消息ID/版本处理，不融合原文。下一条消息立即能读近期原文，即使标签尚未完成；重启恢复、幂等、撤回/更正顺序、用户隔离和安全Key生命周期需要一并实现。后台写记忆的延迟取舍也见[LangGraph官方记忆文档](https://docs.langchain.com/oss/python/concepts/memory#in-the-background)，这里只借鉴结构，不引入其框架或融合画像。

该方向尚未实现；下一验证应包含自然连续分享、隐含回忆、任务指令、事实更正，分开测首字/完整回复、漏召回、无关旧事干扰、标签误判和队列积压。当前结果不能承诺具体优化后的等待时间。

## 使用建议与验证边界

首轮15秒、4096token预算下，开启模式较高的原始断言通过率没有转化为更高的“全部通过且在预算内”次数，两者均13/24。第二轮更宽预算获得21/24完整断言通过，但语义错误仍存在，较长等待也已实测。**本轮只测量，没有更改生产默认。**复杂记忆识别值得结合体验尝试异步处理，并用同一原话版本校验后落标注；是否让记忆处理阻塞用户看见回复，需要看完整等待数据。

这次只评了少量合成语义和固定原文下的回答能力，不含真实用户长期数据、实际BM25/冷索引召回、向量库、并发压测或自然万轮准确率。流式测试另测首个思考片段、首个最终正文与完整返回，不能把思考首字当用户能看到的答案。RAG原文没有融合、改写或删除；模型回答可以结合多个原文解释，但不另存融合事实。本轮只增加测试与文档，应用源码、Docker服务和Android APK未改。

用户提到当前LLM“先思考再回答”会增加全双工难度，是背景说明，不是新增ReAct工具循环需求。与自己的OC全双工通话是后续设想，本轮未实施语音功能。
