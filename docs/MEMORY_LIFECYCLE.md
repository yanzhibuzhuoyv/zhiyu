# 原文保留的三层记忆方案

2026-10-06。**尚未启用自动三层识别或冷索引。** 当前每条成功保存的用户/AI消息仍独立入库、有原文偏移FTS入口。已实现[正式正文无损存储/兼容迁移](BODY_STORAGE.md)与纯策略`memory_lifecycle.py`（输入为已验证原文标注，不从自由文本抽取事实）；118项策略测试验证去重、独立事件、类型/作者/肯否和未解决承诺，不代表自然语言分类准确。已完成的旧耐久记录见[报告](LONG_FIELDS_ENDURANCE.md)。

用户已选择：**保留完整原文，先无损压缩或移出活跃索引、降低检索权重**。允许同时检索多条原文，不做记忆融合、摘要替代或事实改写。这里的“忘记”只调整日常调用中的可见度；完整历史仍可恢复和展示。

## 三层与递进

| 层级 | 适合内容 | 增强与退出规则 |
| --- | --- | --- |
| 中期 | 临时愿望、近期经历、约定/承诺 | 普通琐事随时间降低关注；未解决承诺仍保留pending/overdue状态，日期过了不能自动当作兑现 |
| 长期 | 持续关注的话题、用户明确且反复表达的偏好、生活习惯 | 独立原话的持续性增强权重，类型保持原样；后来更正或否定时，旧说法不再代表当前状态 |
| 永久 | 明确的本人生日/重要日期、确认的重要偏好、明确要求长期记住的内容 | 默认不自动过期；可以直接进入，不必重复三次。允许用户更正、撤回，原记录仍独立归档 |

不是所有内容都必须沿中期→长期→永久依次经过。一次明确说明生日可直接保留；重复的临时愿望也不能仅因次数多就成为永久爱好。生日的主体、具体日期及公历/农历不清楚时保持待确认，不凭消息保存日期猜测。

例如今天、三天后、再隔几天分别说“想吃苹果”，这三条仍是三条原话。可以提高“苹果”话题的关注度、让相关旧话更容易被找回，但不能生成“用户一直喜欢苹果”这一新事实。后来明确说“我一直很喜欢苹果，记住这个”才提供偏好与长期保留的直接证据。也要区分“我每天吃苹果，但不喜欢”中的习惯和否定偏好。

“永久”是保留策略，不表示事实不可更正。新的生日修正关联旧消息为superseded；新的“不喜欢了”优先于旧偏好，不能因为旧记录是永久层就把更正压下去。原生日/旧偏好仍可作为当时说过的话查阅。

## 证据、事实有效性和物理存储分别记录

建议新增以下元数据，不新增拼接的“融合记忆正文”：

| 对象 | 字段与约束 |
| --- | --- |
| 原文标注 | annotation_id、message_sequence、char_start/end、kind、subject、polarity、tier、classification_version；每个标注只指向一条消息的一段原文 |
| 有效状态 | current/superseded/retracted/uncertain；supersedes/corroborates只引用其他标注ID，不保存综合事实句 |
| 事件状态 | event_date/timezone/date_basis可为空，promise_state为pending/overdue/fulfilled/cancelled；角色保持user/assistant，不把AI自己的承诺当用户事实 |
| 索引状态 | message_sequence唯一、active/cold、desired_index_version、materialized_index_version、policy_version；索引缺失和主动冷却是不同状态 |
| 正文编码 | message_sequence、codec_version、UTF-8原字节长度、原文SHA256；读取后仍提供相同消息ID/作者/时间/来源和Unicode字符位置 |
| 决策审计 | 单条标注的旧/新等级、原因、证据ID、规则版本、时间；用于重放和撤回错误决策，不复制原文 |

同一条长消息可能同时包含生日与琐事，需要按区间标注。整条消息的索引/存储优先级至少保护其中最高等级的有效区间，不能因为其他内容不重要而一起失去生日的检索入口。未来如只保留部分活跃片段，仍须能追溯完整原文。

证据计数只接受符合主体、类型和有效状态的独立用户表达。AI回声、模型猜测、检索命中、重排次数、请求重试、同日刷屏和复制同一句话均不增加偏好证据。引述他人、假设、否定和过去状态分别标注。重复愿望可以提高该类话题的关注，不能计入肯定偏好的升级证据。

跨天计数需要声明时区或明确使用经过时间窗口。当前只有UTC created_at，没有用户时区和可靠event_date；它是保存时间，不能冒充当地自然日或真实事件发生日期。升级的次数/时间间隔需经重放评估确定，本方案没有把“三次”写成生产规则。

## 检索顺序与权重实验

先按身份/会话隔离，再按当前查询找到相关候选，检查作者、有效状态和更正关系，之后才让层级、时间和事件状态影响排序。无关的永久生日不能占掉当前问题中直接相关的原话。永久层仍按需检索，不每轮全部塞入模型输入。

保留现有最新相关用户原话的保护机制；后续增加经过证据验证的更正优先规则。最终交给模型的内容仍是多条带ID、角色、时间和偏移的原文。并列召回两条相关经历不等于两件事已经发生在同一天，需要明确关系证据；未确认只能分别提供。

先做单变量消融，保留当前词法/作者权重作为基线。可以试验层级小幅加分0/0.02/0.05/0.10，以及中期7/30天、长期90/180天的衰减窗口。**这些只是候选实验值，不是已验证的最佳参数**；须先校准到相同的评分量纲，不能直接把数值当BM25的固定百分比。永久不因年龄自动衰减，被更正内容也不作为当前事实。

承诺的日期迫近可以增加相关查询中的可见度；日期过去只标记逾期。没有明确兑现/取消原话时仍是未解决事件。AI承诺要保留其作者，不自动增添用户喜好或个人经历。

按对话时间重放以下强反例，再比较权重，不用“选出更多永久记忆”作为效果指标：

| 用例 | 必须成立 |
| --- | --- |
| 多天想吃苹果 | 原话仍是愿望；不自动生成爱好 |
| AI反复说用户喜欢苹果 | 不增加用户偏好证据 |
| 同日重复、同句复制、重复检索 | 不推动升级 |
| 朋友生日/假如今天是我生日 | 不确立用户生日 |
| 本人明确生日、随后更正 | 新记录有效，旧原话保留为被更正 |
| 原永久偏好后来被否定 | 最新明确否定优先 |
| 承诺日期过了但未兑现 | 保留pending/overdue，不擅自标记fulfilled |
| 长消息同时含琐事及生日 | 冷却不会损失受保护信息入口 |
| 外来身份、相似主题不同主体 | 在候选限额前隔离，不交叉召回 |
| 冷却→重启→再查询 | 不被错误补建为全活跃；相关冷原文仍能恢复 |

升级误判率、主体误归属、修正命中率、原文recall@4、冷检索成功率与p50/p95分别报告。识别类型/主体/否定的能力要独立测；人工标注的合成用例只验证策略，不能证明自然语言识别准确。训练/验证按会话、主题及措辞族划分，现有16个词法排序案例只作回归，不作为泛化证据。

## 省空间的实际路径

| 方式 | 对空间的影响 | 必须验证 |
| --- | --- | --- |
| 仅降权/分层 | 仍保留相同正文与索引，几乎不减少空间，还增加少量元数据 | 排序是否更合适；不能宣称数据库变小 |
| 冷消息退出活跃FTS | 减少活跃索引占用，完整原文仍在 | 重启不回灌、冷检索和恢复、隔离、索引覆盖；SQLite空闲页不等于文件已缩小 |
| 每条原文独立无损压缩 | 可以减少正文载荷，保留逐条还原能力 | 全文/元数据SHA、Unicode偏移、分页、近期预算、损坏/展开限制、升级/回滚 |
| 正文移到压缩归档 | 可减轻热库；总占用需要将归档一起计算 | 相同设备仅移动不自动省空间；冷定位目录及按需读取延迟 |

完整原文持续增长时，总存储仍会增长。目标是减少附加索引和重复开销、放慢增长，而不是保证永久固定体积。备份和归档也算总空间，不能把它们从统计中省略。冷层如另建一份同样完整的FTS，则主要是换位置，未必节省总索引。

冷层需要有界、按身份的定位方式和回查路径，例如小目录+压缩块的有限候选读取。目录漏掉的同义线索可能导致召回失败，因此评测必须包括低相关/旧记录恢复、超时反馈及后台再激活；不能承诺所有冷历史仍能瞬时找到。请求一条冷记录后按其原ID再激活，恢复索引需检查版本和当前权限。

索引生命周期落地还有一个前置条件；正文兼容前置已经完成：

1. `MemoryIndex.backfill_batch` 会给缺少片段的消息补建索引。直接删除冷片段后，重启会全部重建。先加入明确的生命周期/索引状态，让补建只处理应该活跃而缺索引的记录，并测试故障与重启。
2. 正文读取已统一解码后按Unicode字符取片段，旧TEXT/新BLOB兼容、指纹和有界展开已实现，20k原文迁移、备份恢复和新写千轮均验证通过，见[正文存储](BODY_STORAGE.md)。这只完成正文前置，不证明冷记忆召回和自动分类正确。

空间实验分别测正文载荷、活跃索引、冷目录/索引、标注/审计、主文件/WAL/SHM、freelist及归档文件。SQLite释放页可以复用，主文件可能不立即变小；物理回收另需空闲时段及备份，不自动在聊天时VACUUM。

## 本轮离线研究

新增 `scripts/eval_memory_compression.py`，在停止的合成SQLite副本上流式评估每条原文的zlib 1/6/9。每条独立编码，9字节版本/类型/长度头计入结果，小内容使用原字节回退。只测编码载荷，不修改源库、不存储替代事实、不迁移生产数据。

逐条比较UTF-8原文和完整行的有序SHA（含消息ID、角色、时间、来源等），验证每个已有片段的字符边界与还原后原文一致。严格检查编码版本、长度、结束标记、尾随数据和16MiB研究展开上限；这一上限不改变应用的消息长度限制。报告不输出聊天正文，也不测模型回复或FTS查询等价。

初步研究结果与限制见[正文压缩研究](MEMORY_COMPRESSION.md)。随后正式正文压缩已进入运行后端，旧TEXT迁移仅在专用副本执行；三层识别/晋升和冷检索尚未启用。纯策略118项反例不替代自由文本分类准确率评估。

## Engram适用边界

2026-10-06复核DeepSeek官方仓库及论文v2（2026-07-12修订）。Engram在模型内部用确定性N-gram寻址查embedding表，再用模型上下文门控选择静态信息；论文也讨论把访问频率不同的表项放到不同存储层。这不是对应用聊天原话的生日/承诺分类或自动删除政策。[官方仓库](https://github.com/deepseek-ai/Engram)、[论文与版本](https://arxiv.org/abs/2601.07372)、[架构章节](https://arxiv.org/html/2601.07372v2)。

应用侧可以借鉴确定性定位、按需加载和相关性门控，这是我们的工程推论。API Key无法改变厂商模型的内部embedding表或hidden states，也不能让整套RAG自动获得常数时间与零遗漏。原文仍独立保存；若增加语义向量编码器，要另测模型、量化、召回和存储成本。本方案不声称复现或集成了Engram。

## 落地顺序

正文读取抽象、旧格式兼容及副本无损/分页/检索等价已完成。下一步加入有版本的原文标注和索引状态，以关闭默认方式按时间重放分类/晋升策略；之后实现可恢复的活跃/冷索引，测试重启与异常回滚。最后用独立验证集选择权重和启用策略。没有分类准确率与冷回查证明之前，不自动将任何生产原话移出索引。
