# 聊天存储与空间维护

应用保留连续聊天原话，不自动按时间删除历史。`messages.content`只保存一份正文；双方每条消息另建contentless FTS词项与字符位置索引，查询通过位置读取原文，不产生融合记忆或另一份正文。原文、索引和文档资料仍会随使用增长；优化减少额外开销，不能让无限保存的聊天维持固定大小。

## 历史分批读取

新客户端使用：

```http
GET /api/conversations/{conversation_id}/history?limit=100
Authorization: Bearer <session_token>
```

响应包含 `messages`、`has_more` 和 `next_before`。每页消息按原始时间顺序排列，首次读取的是最近一页；需要更早历史时传入上一页的 `next_before`：

```http
GET /api/conversations/{conversation_id}/history?limit=100&before=<next_before>
```

- `limit` 默认为 100，允许 1–100。SQL 只读取 `limit + 1` 行，用多出的 1 行判断是否还有历史。
- `before` 为消息 ID，按数据库内部递增顺序排除该消息及更新消息，不依赖客户端时间或不稳定的页码。
- 游标必须属于同一身份、同一会话；不存在、跨会话或跨身份均返回 404。过长或空游标、无效 `limit` 返回 422。
- 每页返回正序消息。`has_more=true` 时 `next_before` 为本页最早消息 ID；到头或空会话时为 `null`。
- 读取期间的新消息不会移动此前页面的边界。用户删除游标所在会话或消息后，该游标不再可用。
- 原 `GET /api/conversations/{id}/messages` 继续返回完整数组，兼容旧客户端；它仍可能读取大量数据，应优先使用新分页接口。

分页降低单次网络响应与客户端内存，不删除历史，也不减少数据库中原始消息数量。长对话模型输入另有最近 20 完整轮和早期记忆检索预算，见 [连续聊天记忆](CONVERSATION_MEMORY.md)。

## 文档来源无损压缩

一条 AI 回复的 `sources` 会保存本次引用的文档片段，以便原始文档后来删除后，用户仍能查看当时的参考内容。重复引用同一资料时，这些片段会带来额外磁盘占用。来源压缩阶段正文仍为TEXT；2026-10-06另已实现[正文的独立无损存储与兼容迁移](BODY_STORAGE.md)，旧TEXT继续可读，原文检索使用解码后的字符偏移。

- 小来源继续保存紧凑 JSON TEXT；JSON UTF-8 字节数达到 **1,024** 后，尝试 zlib 压缩。
- 只有压缩结果连同头部至少节省 **25%**，才写入 SQLite BLOB。难以压缩的资料保留 TEXT，避免不必要的开销。
- 新 BLOB 格式为版本标记 `ZYSC1\0`、4 字节原 JSON 长度和 zlib 流。来源 JSON 展开上限为 **1 MiB**。
- 读取同时支持已有的 JSON TEXT 和新 BLOB。检查版本、长度、UTF-8、JSON 类型、有限数值、zlib 流结束及尾部；损坏或展开超限返回安全的 503，不回显原始资料。
- API 返回与原始来源相同的数组，不要求 Android 解压或适配 BLOB。
- 对旧 `sources TEXT` 字段直接写入 BLOB 是 SQLite 支持的值类型，因此不需要表结构迁移。没有自动重写旧记录；原有 TEXT 继续可读，新写记录才适用压缩。
- 若来源编码失败，保存事务会整体回滚，不留下用户消息或 AI 半轮。

## 来源压缩阶段实测体积（加入聊天FTS前）

`tests/test_history_storage.py::test_synthetic_database_footprint_is_smaller_without_changing_messages` 在临时目录构建两个相同规模的库，各有 **160 个完整聊天轮次**，每轮 AI 回复都附带 **5 段重复中文资料**。对比库使用原来的 JSON TEXT，新库使用透明压缩；消息内容相同，往返读取内容相同。先完成 WAL checkpoint，再测量主数据库文件。

| 合成场景 | 主数据库体积 |
| --- | ---: |
| 原 JSON TEXT 来源 | 2,195,456 字节 |
| 新压缩来源 | 147,456 字节 |

此重复资料场景约减少 **93.3%** 的主数据库占用，包含该场景的消息与索引。不能据此承诺真实聊天总体也减少 93.3%；若没有文档来源、来源短小或主要空间来自聊天正文，节省会明显较小。原始消息、文档和索引仍需占用空间。

## 删除、备份和手动回收

2026-10-06双方长字段万轮已完成20,000消息及全部检查点，主库540.20MiB、原文215.45MiB、索引306.05MiB；最终单条级联删除因128MiB临时文件空间耗尽而失败，整轮报告保留failed。现删除改为一个外层事务内分批处理，最多768消息与8MiB编码内容预算；超大旧单条可能超过预算，不能视为绝对临时文件上限。错误完整回滚并返回安全503，工作线程保持health响应；整个删除仍持SQLite写锁。

新生产镜像实际删除20,000条副本消息约98.70秒，第19,001条注入错误时原文/出处/片段哈希与FTS rowid清单回滚一致，integrity通过；其他会话保留、FTS integrity/quick_check通过，源卷只读且三文件哈希未变。副本主库删除后702,828,544B、171,574空闲页，说明大事务可以让文件先增长，不能承诺删除马上变小。完整记录见[长字段耐久](LONG_FIELDS_ENDURANCE.md)。这些测试没有删除用户历史或维护原8791卷。

逐消息FTS加权版真实10,000轮/20,000消息通过：主库42,430,464B，FTS及片段相关分配18,010,112B，原始双方正文共18,954,219 UTF-8字节。仅删除自己的3个测试会话后恢复基线8条消息/8片段，主库仍42,430,464B，但10,342个页空闲可复用。没有自动删除用户历史或VACUUM。完整采样、负载和限制见[长聊实测](LONG_CHAT_TEST.md)；这是演示短回复的合成负载，不是所有真实聊天的体积估计。

SQLite 删除记录后，空闲页可供后续写入复用，主数据库文件通常不会立刻缩小；WAL 日志文件的大小也应单独检查。日常聊天不自动执行 `VACUUM`，因为重写整个数据库会占用临时磁盘、锁住写入，并可能花费较长时间。

补充双方长字段真实HTTP冒烟：36条user16k、32条AI16k＋4条AI64k，另短轮次与检索共134消息，原文3,298,256B、索引4,911,104B、主库9,302,016B。长文中尾、重启后全部hash和偏移覆盖通过，见[长字段报告](LONG_FIELDS_TEST.md)。后续千轮/万轮采用普通user2k–4k、AI4k–8k及16k/64k边界，独立结果见[长字段耐久](LONG_FIELDS_ENDURANCE.md)；上述冒烟不等于所有轮都达到极限长度的万轮测试。

需要把空闲页还给文件系统时，由维护人员选择空闲时段执行，先完成以下准备：

1. 停止后端写入，确认相关容器或进程确实已停止；保证足够临时空间，至少留出该数据库体积两倍的可用空间。
2. 备份完整数据目录，包括 `identity.secret`、`chat.sqlite3`、`rag.sqlite3` 及尚存在的 `-wal`/`-shm` 文件；不要在后端仍写入时仅复制主 `.sqlite3` 文件。也可使用 SQLite backup API 制作一致性数据库副本，并单独保存身份密钥。
3. 在备份副本上先运行 `PRAGMA integrity_check;`，确认结果为 `ok`，核对会话和消息数量，并实际读取 TEXT/BLOB 混存的来源。保留备份，直到原库维护后的应用读取验证完成。
4. 对确定的原始数据库依次执行 `PRAGMA wal_checkpoint(TRUNCATE);`、`VACUUM;` 和 `PRAGMA integrity_check;`。`VACUUM` 不能放在另一个事务内。对知识库也可单独进行同样的受控维护。
5. 启动后端，用原 Key 验证历史、来源和记忆，再记录前后文件体积。磁盘回收只是物理整理，不会删除仍保存的聊天。

本版没有自动压缩旧来源的批量迁移脚本。若以后提供可选旧资料迁移，应使用新版本来源编解码器，先验证完整备份，再按有限批次、单事务更新，记录前后行数与字节数，并逐条验证还原内容相等；不能直接对 `content` 做压缩。恢复到不认识新 BLOB 格式的旧程序前，应还原维护前备份或明确转换来源格式，不能直接让旧版 `json.loads` 读取新 BLOB。

备份包含私密聊天、资料和身份密钥，应保存到受控位置。这里描述的是可选择的维护流程；本轮测试未维护或读取用户实际数据库。
