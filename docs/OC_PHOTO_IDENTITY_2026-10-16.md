# 恋人认出自己的 OC 图片

过去的照片上下文只提供最近用户图片和自动观察；没有附上当前恋人的 OC 归属或参考图，模型无法可靠知道“这是我”。单纯要求模型拟人不能补上这项缺失证据。

本轮用 `OcPhotoIdentitySnapshot` 绑定当前确认的 profile 视觉版本、参考图 ID/SHA，以及与当前参考匹配的已保存 OC 档案和它的导入原图。用户上传图片与当前参考或原始导入图 SHA 完全相同时，可确定它是当前恋人的设定形象；此结论来自用户设置的图片归属，不是推断现实人物身份。它不证明模型看到未提供的画面细节，也不产生虚构记忆。

其他图片在模型具备已验证原生视觉能力时，额外提供当前 OC 参考图用于对照。该参考单独放在原用户图片前的应用图块，不写入聊天或 RAG，不改写用户原文；用户原文本来为空则继续为空。参考副本最长边约 512 像素、最多 512 KiB，两张图合计仍不超过现有 5 MiB，且每个 provider 消息最多一张图。消息数没有余量、当前图已用完预算、参考缺失/损坏或副本无法压进预算时，保留主图发送并退回不确定，不为可选参考破坏发送。

非多模态模型只有同原图 SHA 的归属证据可以确定。其他图仍按现有 OCR/观察能力处理，不假装对照过人物。应用证据、图片/OCR 的低信任内容、用户原文相互区分；图片或参考中的文字不能成为指令。回复要求使用恋人自己的口吻，不暴露校验、档案或检索措辞。

`LocalPhotoPromptContext.ocIdentity` 返回实际使用的快照；请求后的最终持久化需要在当前 profile/OC 的短检查边界重新捕获并比较，以阻止形象更新后的旧回答落库。这由 repository 接线承担，helper 不持有 UI、数据库或 Key。

7 项 JVM 合同和 3 项原生合同已实跑 TODO RED；主线程/消息与素材均使用隔离测试空间、合成图片和 fake transport，没有调用真实 Key 或付费 API。原生合同包括真实 PNG、两张图片的 provider JSON、原文和图片原字节保持、可选参考缺失的降级。最终 GREEN 与完整回归见本轮主报告，不把单元合同当作实际云模型识图准确率。
