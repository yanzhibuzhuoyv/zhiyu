### 47：中午被当成深夜

实际请求有当前手机时间，但旧聊天只有正文，模型可能把昨晚的“还早、晚些睡”沿用到今天。新请求保留每条原话，另加发送时间、跨日信息，并把本轮设备时间与本地时段贴到最新输入旁；普通聊天、通话、主动消息和日常分享一致接入。参考 OC 图片不冒作用户新消息。标注只用于发送给模型的副本，不写回原文，不改检索和事件时间。

首次只加长系统提示的真实测试仍出现“夜里安静”，已拒收；没有把代码编译成功算作语义成功。随后对比精简提示与逐条标注，再验证本轮当前时间锚点。真实 DeepSeek Flash 对照共五轮、136 次合成聊天请求，均完整返回；无新生图收费，Key 不打印、不入包或 Git，凭证文件 SHA 保持。中间诊断提示不冒称生产实现，最后 r5 使用实际 Kotlin 生产提示及标注导出。

最终 r5 的 16 条新方案回复中，普通中午“吃完饭”与“午饭没吃”四次均未延续深夜或反转完成状态；保留截止时间、夜班、昨晚引用与真正凌晨的控制。故意报错时间时，模型仍可能理解为时差并追问：这是已知自然语言局限，不宣称任意表述下都不会误判。原有明确当前小时纠偏继续生效；没有用字符串把所有“晚”改成“早”，也没有每轮增加一次审稿模型。

另将实际 Android Repository 序列化请求直接导出，保留真实组合后的时间/媒体/日历系统提示，仅替换合成用户原话，追加五次官方模型验证，均完整返回。因此本轮真实文本请求合计141次。原句得到“吃完就好。中午吃得香吗？”，未吃午饭、引用昨晚和夜班也区分了中午；故意错报时仍出现无依据的睡眠推测，保留为已知局限，不改写输出冒作全部语义通过。

r5 完整响应中位数：对照 1.3345 秒、新方案 1.436 秒，各 16 次。样本小且受服务波动影响，不是手机延迟或统计显著性结论。分轮原文、完整响应、token 与耗时位于私有 `artifacts/feedback4749-temporal-live-ab-r*.json`，API Key 不在这些文件中。

### 48：画面正常但人物看不出运动

已在实际编辑预览和保存重开后的通话中复现：大原图缩到手机预览，旧动作仅约 0.069dp / 0.291dp。之前“GPU 有像素变化”不足以证明看得出动作。

Android 共用驱动提高有界头部输入，约五秒往返；背景、原图、标注、眼口通道、强度零和旧包不改写约束保留。新增真实 PixelCopy 测量要求脸部标记至少移动 1.2dp，独立背景变化不超过 0.05dp，覆盖大图、小头部、半强度、零强度及旧包 SHA 不变。另修复新增头部驱动在 60 秒边界的不连续，portable rig2d 默认不变。

已有非零头部动作的旧包直接受益；没有头部层、被全部擦除或强度零仍需人工修正。单图局部动画仍不是自动完整 Cubism，也不保证任意 OC 画质。[手机教程](LIVE2D_PHONE_GUIDE_ZH.md)

### 49：后台主动联系间隔

用户已确认旧版在后台/锁屏收到过通知。这证明至少一次送达，不说明昨夜究竟命中普通联系、日常分享或何种限制。

查到旧政策等待期限可能在新交流后仍挡住服务重新判断；真实聊天成功也未解除旧连接拒绝退避。现在仅在新的持久用户消息后使旧政策快照失效，或用真实 provider 完成时刻解除对应旧连接退避。本机短答不证明 Key 恢复；迟到提交不能覆盖更晚的新连接错误。重复事件不推迟已释放期限。

显式验证原先可能 REPLACE 一个正在运行的工作，现改为保留身份的更新与已有独立恢复检查；测试实际运行状态，而非只比 pending ID。保留用户关闭/暂停、真实网络、通知许可、人物频率、每日上限、未回复政策及未确认付费请求。没有简单加大发送频率，也没有额外加入夜间静默时间；删掉了设置页残留的 22:00–08:00 旧说明。[具体间隔和手机边界](FEEDBACK_49_PROACTIVE_2026-10-19.md)

- 39 项首次集成 Native 已通过，222.785 秒；包含实际页面运动、照片提交及主动联系恢复。其后新增边界不以此代替最终验收。

- 首 Live2D PixelCopy 没首帧、首空图库被 seed 污染属于夹具问题，修夹具后才记录对应业务 RED。lint 的 API 注解曾失败；SdkSuppress 不在现有编译 classpath，最终测试类使用精确 lint 抑制与 API29 运行前提，当前模拟器六项未跳过；不加依赖。
- 首完整 Native r1 因独审发现上述图片问题，由 root 主动停止以纳入修复；末尾 `Process crashed` 是对自有测试进程执行 force-stop 的结果，不是全绿或新生产崩溃结论。r2 随后有一项在调用连接修复之前等待真实 OS 进入 Worker 30秒超时；相邻派发控制通过。此项开始等待统一为其它系统测试已有的90秒，仍须真实RUNNING、同ID/pending与零provider，超时仍明确失败并带状态；生产不改。最后r3完整481/481通过（607.828秒），以该实际完整结果验收，不把延长等待称为手机准时性修复。
